# Phase 03 Plan 03: Run The Training Job

## Goal

Turn a validated Dataset Manifest into a trained adapter on this machine, with
progress that reports what is actually happening, a job that survives the app
being closed, and a published result whose lineage says exactly what produced it.

This is the plan that makes the product do the thing it is named after. Nothing
before it trains anything.

## Preconditions

- Plan 03-02 has produced a validated Dataset Manifest.
- The manifest carries `captureTier`, `textProvenance`, an `instruct` string per
  segment, and a deterministic dev split — the three fields 03-04 asked 03-02 to
  absorb.

### The training runtime does not exist yet

Measured on 2026-09-03: `.runtime/omnivoice-studio/.venv` has `torch 2.8.0+cu128`
and `torchaudio`, and **none of `omnivoice`, `accelerate`, `peft` or
`webdataset`**. The STT sidecar was never a training environment.

So this plan begins by provisioning one, and that is not a footnote: it is
multi-gigabyte, it is the first thing plan 07-01's `ModelStore` will have to
manage, and it must not be attempted silently while a user waits at a progress
bar. Provisioning is its own visible step with its own failure state.

### One GPU, already shared

`nvidia-smi`: a single RTX 3090, 24 GB, with ~6 GB already resident. About 18 GB
free, which is comfortable for LoRA over a 0.6B backbone and nowhere near enough
for a full fine-tune of anything larger.

That GPU is already wanted by Faster-Whisper and by pyannote. Training holds it
for hours. **A single GPU lease is therefore part of this plan, not a later
refinement** — without it, a transcription queued during training will either
fail on out-of-memory or slow the run to a crawl, and neither failure will point
at its cause.

## The nine steps a run passes through

This list is the progress contract. The UI reads it, and the visualisation the
owner asked for is built from it rather than from a percentage.

| # | Step | Where | Duration | What it can report |
| --- | --- | --- | --- | --- |
| 1 | Provision runtime | disk | once, minutes | Package, bytes, cached or fetched |
| 2 | Resolve base model | disk | once, minutes | Model id, hash verified |
| 3 | Read manifest | API | seconds | Segments accepted, rejected and why |
| 4 | Write JSONL | API | seconds | Lines written, train/dev counts |
| 5 | Tokenize audio | GPU | minutes to tens of minutes | Shards done, samples, seconds of audio |
| 6 | Load model and attach LoRA | GPU | 1–3 min | `trainable params` percentage |
| 7 | Train | GPU | **hours** | step, loss, learning rate, steps/sec, VRAM |
| 8 | Checkpoint | disk | every `save_steps` | Step, path, bytes, kept vs rotated |
| 9 | Merge and publish | CPU/GPU | minutes | Output path, similarity gate result |

Step 7 is the whole job by wall clock. A percentage there is nearly meaningless
— what tells a person whether to keep waiting is **the loss curve**, and whether
dev loss is still tracking train loss. Emit both per `logging_steps`, keep them
in the job record, and let the UI draw them.

Steps 1, 2 and 5 are the ones that make a first run feel broken, because they are
long, silent and happen before anything recognisable as training. Each must
report its own units, not a spinner.

## Process shape

`accelerate launch` spawns child processes and holds the GPU for hours. Three
consequences:

**It runs as a sidecar, not inside the API.** A training run that lived in the
API process would take the workspace down with it on a CUDA error, and would die
whenever the API restarted to pick up a code change.

**Every child must be inside the launcher's Job Object.** W0 already learned this
for the existing workloads: a process tree that escapes the Job Object survives
the app closing and keeps the GPU. `accelerate` makes a deeper tree than anything
the launcher currently owns, so this needs verifying rather than assuming.

**Progress comes from a Pro4Bro runner, not from the engine.** `engines/OmniVoice`
is read-only, so no hook goes inside it. A runner script outside the checkout
invokes the CLI, parses its logging lines and writes a JSONL progress file the
API tails. TensorBoard event files are the engine's own output and are not a
progress API; read them only if the parse proves unreliable, and say so if it
does.

## Job records and recovery

A run lasts hours, so the app being closed mid-run is normal, not exceptional.

```
<project>/jobs/training/<run-id>/
  run.json          # config, manifest hash, engine revision, step, status
  progress.jsonl    # one line per logging step; append-only
  data/             # JSONL manifests and tokenized shards for this run
  checkpoints/      # checkpoint-<step>/ as accelerate writes them
```

`run.json` is the source of truth for resumption. On startup the API finds runs
in a non-terminal state and reports them as *interrupted* — never as running,
because the process is gone. Resuming sets `resume_from_checkpoint` to the last
complete checkpoint; `init_from_checkpoint` and every `lora_*` field must match
the original run or `accelerate` fails on a shape mismatch, so they are read back
from `run.json` rather than rebuilt from current settings.

Cancellation kills the process tree, marks the run cancelled, and **keeps the
checkpoints**. A cancelled run at step 4,000 is a resumable run, not a mistake to
clean up.

## Output: a Voice Model Set, not a checkpoint

Per plan 03-04, a speaker's emotions are separate LoRA adapters that publish
together. So a run produces one adapter, and a set publishes only when all its
members exist and pass:

- the same base checkpoint and the same anchor slice, recorded by segment id;
- a speaker-similarity gate per adapter against the speaker's reference clip;
- lineage: manifest hash, engine revision, config, dataset segment count, the
  exact steps trained.

The similarity threshold is **not to be invented here**. Measure it across the
first real sets in the R5 pattern — state the threshold first, measure, be
willing to decline — and record the number with its evidence.

## Tasks

1. Provision a training runtime as an explicit, resumable, visible step;
   report what it fetched and what it reused.
2. Define a `TrainingRunner` port and a `run.json` / `progress.jsonl` schema
   versioned from the start.
3. Write the JSONL manifest and data config from a Dataset Manifest, including
   the deterministic dev split and the per-segment `instruct` string.
4. Wrap `extract_audio_tokens` with per-shard progress.
5. Wrap `accelerate launch` in a runner that parses logging lines into
   `progress.jsonl`, with every child inside the launcher's Job Object.
6. Add a single GPU lease that STT, diarization and training all acquire, so a
   queued transcription waits instead of colliding.
7. Surface the nine steps, the loss curves and the checkpoint list in Training
   Job; no fabricated percentages.
8. Add cancel, and resume-from-interrupted driven by `run.json`.
9. Merge the adapter and publish a Voice Model Set with full lineage.
10. Add the similarity-gate probe with thresholds stated before it runs.
11. Tests: manifest to JSONL, dev split determinism, progress parsing against
    recorded output, interrupted-run detection, resume config equality, lease
    contention, cancellation leaving checkpoints intact.

## Verification

- A run reaches a checkpoint on real project audio, and the checkpoint loads.
- Killing the app mid-run leaves no orphaned GPU process, and the run reappears
  as interrupted rather than running.
- Resuming continues from the last checkpoint at the right step.
- Starting a transcription during training waits for the lease instead of
  failing on out-of-memory.
- Cancelling at step N keeps `checkpoint-N` and the run resumes from it.
- Progress lines match what the engine actually printed; a parse failure shows
  as unknown rather than as a plausible wrong number.
- A published set records the manifest hash and engine revision that made it.
- Re-running an unchanged manifest produces the same JSONL and the same split.

## Not in this plan

- Generation and stitching. A trained set is the deliverable; using it is 05.
- The emotion `instruct` conditioning probe.
- Multi-GPU and remote training.
- VibeVoice. The exporter seam exists; no adapter is written here.
- Full fine-tuning. LoRA only — 18 GB of free VRAM and per-emotion adapters make
  that a requirement rather than a preference.
