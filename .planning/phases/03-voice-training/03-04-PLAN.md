# Phase 03 Plan 04: High Quality Voice Training

## Goal

Add a guided capture mode in which the speaker reads app-supplied material while
the app follows the words live, so that a Dataset Manifest can be produced from
audio whose transcript is **known before the microphone opens** rather than
recovered afterwards.

This is not a second training pipeline. It is the highest-quality source tier
feeding the same compiler, manifest, and training job as imported footage.

## Why this is the cheap path, not the expensive one

Plan 03-02 has to solve two hard problems for imported footage: what was said,
and where each segment starts and ends. Guided reading removes both.

- **Text is ground truth.** The card the user read is the transcript. ASR is
  demoted from source-of-truth to a verifier that answers one question — did the
  speaker actually read this card?
- **Segment boundaries are file boundaries.** One card is one take is one file.
  Nothing has to be cut out of a longer recording, so the alignment accuracy
  that R5 measured and declined (`docs/STABILIZATION-LOG.md`) does not gate this
  work at all. R5's own closing note already separates the two questions.

Everything downstream — speaker ownership, emotion labels, `trainingSelected` —
is set at capture time instead of being annotated later.

### Common denominator

Both engines want the same thing and differ only in packaging:

```
(24 kHz mono WAV, 2–15 s, exact transcript, speaker, language)  +  30–60 s clean reference clip
```

The existing importer already writes exactly this format —
`media_import_processor.py:487` extracts `-ac 1 -ar 24000 -c:a pcm_s16le`. No
new audio path is needed; the Reading Studio reuses it.

Therefore: **one Dataset Manifest, N exporters.** The user picks the target
engine in Train; the compiler emits the neutral manifest; a `DatasetExporter`
port writes the engine's layout (`JSONL + data.lst` for OmniVoice, HF dataset
directory with `Speaker 1:` prefixes for VibeVoice). Engine specifics never
reach a UI module, per the standing adapter rule.

**Do not train from MP3.** The video-to-MP3 export is a delivery convenience and
should stay one; a lossy round trip before an audio tokenizer throws away exactly
the high-frequency detail the tokenizer encodes. Keep the original as `source.*`,
train from `analysis.wav`, and offer MP3 only as an export action.

## Emotion at generation time

The owner's question: after training, can the engine be *told* an emotion at TTS
time? Answer, from the checkout rather than from marketing copy:

**Neither engine ships an emotion control today.**

- OmniVoice's `instruct` has exactly six categories — gender, age, pitch, style
  (whose only value is `whisper`), English accent, and Chinese dialect
  (`docs/voice-design.md`). There is no emotion category. It does support inline
  non-verbal tags in the text — `[laughter]`, `[sigh]`, `[dissatisfaction-hnn]`,
  the `[surprise-*]` and `[question-*]` families (`README.md:259`) — which colour
  a line but do not set its delivery.
- VibeVoice has no emotion parameter at all. Emotion is carried by the voice
  prompt and by the surrounding text.

So today, on both engines, **emotion transfers through the reference audio.**
That is precisely why per-emotion reference clip harvesting is the first thing
this plan should ship: a word tagged `angry` in Script generates from an angry
reference clip, and the emotion arrives as prosody rather than as a label.

### The opening this plan should keep

OmniVoice's training pipeline reads the instruct string **per sample from the
JSONL metadata**:

```python
# omnivoice/data/processor.py:97-106
if use_instruct:
    instruct = sample["label"].get("instruct", "None")
...
style += f"<|instruct_start|>{instruct}<|instruct_end|>"
```

`instruct_ratio` and `only_instruct_ratio` are training-config fields
(`omnivoice/training/config.py:51-52`, defaults `1.0` / `0.5`), and both finetune
example configs set them to `0.0` only because those examples have no instruct
data to give.

That means a fine-tune **can teach a new instruct attribute**: write
`"instruct": "angry"` into each segment's JSONL line, raise `instruct_ratio`, and
the model learns to condition on it. After merging the adapter, `generate(text=...,
instruct="angry")` becomes a real control surface, and Script's existing emotion
labels map straight onto it.

This is an opening, not a promise. It is unverified, it needs materially more
per-emotion audio than pack v1 carries, and teaching a token the base model never
saw in that role can degrade the attributes it already knows. It is a probe for a
later plan, in the shape R5 established: state the threshold first, measure, and
be willing to decline.

What this plan must do now is **not close the door**: carry an `instruct` field
per segment in the Dataset Manifest, derived from the segment's Emotion Label.
Exporters that cannot use it drop it. Adding it later means a manifest version
bump; adding it now costs one field.

### Decided: one adapter per emotion, stitched at generation

The owner has settled the approach while no engine carries emotion natively:
train a separate model per emotion for a speaker, generate each span with the
model matching its Emotion Label, and join the spans. Consequences this plan and
03-03 must respect:

1. **LoRA, never full fine-tune, for the per-emotion models.** Nine emotions as
   nine full checkpoints is not a thing anyone can ship; nine adapters of tens of
   MB over one shared base is routine. This makes `use_lora: true` a requirement
   of the emotion feature, not a preference.
2. **Anchor identity across the set.** Each emotion adapter trains on that
   emotion's cards **plus a fixed slice of the neutral core**. Without the
   anchor, nine adapters drift apart in timbre and a stitched line sounds like
   nine different people rather than one person changing mood. The neutral slice
   must be the same slice for every adapter in a set, recorded in the manifest.
3. **Batch by emotion, not by timeline order.** Swapping adapters per span is
   expensive. Generate every `angry` span in one pass, every `sad` span in the
   next, and reassemble into timeline order afterwards. This belongs in the
   generation job's scheduling, not in the UI.
4. **Pin everything that touches a seam.** Identical `num_step`,
   `guidance_scale`, and sampling temperatures across the whole line; loudness
   match at each join; a short crossfade. OmniVoice's `postprocess_output`
   strips trailing silence by default and `pad_duration` / `fade_duration`
   reshape the edges (`docs/generation-parameters.md`) — pin all three per
   line, or the joins will drift.
5. **Voice Model gains an emotion field and a set identity.** Voice Vault has to
   show "speaker · emotion · version" and know which adapters were trained as one
   anchored set, because mixing adapters from different sets reintroduces exactly
   the drift item 2 prevents.
6. **Pack v2 moves onto the critical path.** Nine adapters need materially more
   than the ~1 minute per emotion v1 ships. This is the reason to extend the
   emotion passages, and it is now a dependency of a feature rather than a
   nice-to-have.

The `instruct` field stays in the manifest regardless. If the conditioning probe
later works, one adapter with an emotion instruct removes every seam in the list
above; keeping the field costs nothing and keeps that door open.

### Identity lock — a product rule, not a recommendation

The owner's requirement: once a voice is chosen, **every generated span is that
same person**. Emotion changes the state, never the identity. The system must not
be *able* to emit a different voice.

That upgrades the anchoring in item 2 above from good practice to an enforced
constraint, in four places:

1. **Voice Model Set is the unit, not the adapter.** A set is one Speaker
   Profile, one base checkpoint, one anchor slice, and N emotion adapters trained
   together. Adapters are addressable only through their set. Voice Vault offers
   sets; it never offers a loose adapter.
2. **The anchor slice is recorded and identical.** Every adapter in a set trains
   on its emotion's segments plus byte-identical neutral segments, listed by
   segment ID in the set manifest. A set whose members disagree on the anchor is
   invalid and cannot be published.
3. **A similarity gate after training, before publishing.** For each adapter,
   generate a fixed probe line, embed it with a speaker-verification model, and
   compare against the speaker's reference embedding. Below threshold the adapter
   is marked `drifted` and the set does not publish. The repo already installs
   pyannote for diarization, so an embedding model is present rather than new.
   **The threshold must be measured before it is fixed** — pick it from a probe
   across the first real sets, in the R5 pattern, not from a number someone liked.
4. **Generation refuses to cross sets.** A line whose spans resolve to adapters
   from two different sets is rejected at job build time, not blended and shipped.

Retraining one emotion re-opens the gate for the whole set: an adapter that
passed against an older reference is not evidence about a new one.

Honest limitation: a similarity gate catches *drift*, not every artefact. Two
adapters can both pass and still sound subtly different at a join. The gate is a
floor under the failure mode the owner named, not a guarantee of seamlessness —
which is why the join rules in item 4 of the previous section still apply.

## Dataset size targets

The owner's targets: 10–15 minutes for neutral/normal, 4–5 minutes per emotion.

**These are not too long, and the question conflates two different limits.**
The 2–15 second ceiling is per *sample*, not per session. Minutes recorded and
seconds per sample are independent: Flow mode turns a long read into many short
samples, which is exactly what both engines want.

| Target | Words @140 wpm | Samples @8 s | What the engines see |
| --- | --- | --- | --- |
| Neutral 12.5 min | ~1,750 | ~93 | 93 in-range samples |
| One emotion 4.5 min | ~630 | ~33 | 33 in-range samples |
| Full set: neutral + 8 emotions | ~6,790 | ~363 | ~48.5 min, a healthy LoRA dataset |

The only way these figures break a limit is feeding 15 minutes as **one file** —
900 s against a ~15 s ceiling, dropped outright by `--max_length`. Nothing in
this plan does that.

Three real consequences of the larger targets:

- **Session length.** ~48 minutes of usable speech is roughly **1 hour 45 of
  sitting**, once count-ins, retakes and breaks are counted. That must be
  resumable across sittings, which the session ledger already allows, and the
  UI must show minutes owed per emotion so a user can stop anywhere.
- **Vocal fatigue works against the identity lock.** A voice at minute 50 is not
  the voice at minute 5, and that within-speaker drift lands in the training data
  where the similarity gate cannot see it. Mitigation: enforce a break every
  ~10 minutes, re-run the Capture Check after each break, and warn when level or
  median pitch drifts materially from the session's opening measurement.
- **VibeVoice prefers longer samples.** Its community docs warn that a
  few-seconds-only dataset makes the model struggle with long-form output. Since
  Flow mode preserves cross-sentence prosody, the VibeVoice exporter should
  **merge adjacent accepted spans** into longer samples while the OmniVoice
  exporter keeps them at 2–15 s. Same manifest, two packings — the exact upper
  bound for the merge is verify-on-integration.

**Mix at the pipeline level, separate at the policy level.**

| Question | Decision | Reason |
| --- | --- | --- |
| Separate project type in Project Hub? | **No.** Nothing changes in Project Hub — no preset, no second project class. | The owner settled it: guided reading is a recording mode, not a kind of project. Users routinely start with footage and decide on guided reads later. |
| Separate page or full-screen route? | **No.** An **HQ toggle inside Recorder**. Flipping it turns Script into the teleprompter and hands Recorder the reading plan. | Recorder and Script already sit side by side on Speech to Text — right column and centre. The mode reuses that composition instead of inventing a route, and it leaves Voice Training's "no Recorder module" contract from 03-01 untouched. |
| Separate dataset? | **No, but tiered.** Every asset carries `captureTier`: `guided` \| `record` \| `import`. Default policy for a speaker's first model: `HQ only`. Footage becomes an
augmentation run afterwards, and mixing tiers whose measured noise floors differ
by more than 10 dB raises a visible warning rather than being blocked.

### Where HQ mode lives

Recorder gains one switch: **Normal / HQ**. In HQ the module shows the reading
plan (speaker, language, pack, which emotions, minutes still owed) instead of the
free-recording controls, and Script switches from transcript editor to
teleprompter for the duration of the session.

Consequence to accept: Recorder exists on Speech to Text and Voice Manipulator,
never on Voice Training. So guided **capture** happens on Speech to Text and the
resulting blocks flow to Voice Training for dataset and training. That is a
little odd to read on a page menu, but it is what the 03-01 page contracts say,
and inventing a second Recorder on Voice Training to fix the wording would be
worse. Revisit when Phase 04 makes module placement user-controlled.

## New domain terms

To add to `CONTEXT.md` on approval:

- **Reading Pack**: app-level, read-only reading material — passages of cards in
  one language, each passage carrying one Emotion Label and a delivery direction.
- **Reading Card**: one utterance intended to be one take, 2–15 s of speech.
- **Reading Session**: a project-owned capture run pairing one Speaker Profile
  with a selected set of passages, holding takes, QC results, and coverage.
- **Capture Tier**: `guided`, `record`, or `import` — how an asset's audio and
  transcript came to exist. It is provenance, not a quality score.
- **Capture Check**: the pre-flight measurement of a recording chain (peak
  headroom, noise floor, clipping) stored with the session.
- **Voice Model Set**: one Speaker Profile, one base checkpoint, one anchor
  slice, and the emotion adapters trained together against them. It is the unit
  a user selects and the unit that publishes; a single adapter is never
  addressable on its own.

### What a card is, concretely

A **card** is one sentence to be read in one breath — the unit of the reading
material, not a unit of the Media Pool. Worked example, a full 11-passage
Vietnamese session:

| Level | Count | Where it lives | What it is |
| --- | --- | --- | --- |
| Card | 112 | the shipped pack, snapshotted into `session.json` | the text on screen |
| Take | 112+ (more with retakes) | `takes/*.wav` inside the session folder | one small WAV, 2–15 s |
| Training sample | 112 | the Dataset Manifest | one take plus its exact text |
| **Media Pool row** | **11** | `index.json` | one block per (session, emotion) |

So a session that produces 112 training samples adds **11 rows** to the Media
Pool, one per passage-emotion block, each playable and scrubbable like any other
footage. The takes are training data living inside the session folder; they are
not footage and never appear as footage rows.

This split is deliberate. Training wants many small files with exact text;
review wants a few long ones. Registering every take as an asset would give the
user 112 near-identical rows to scroll and would undo the W1 index work
(`media.list` 3.3 s → 0.094 s, `index.json` 31.3 MB → 3.05 MB).

## Capture contract

### 1. Pre-flight (once per session, cached per device)

1. Device selection reuses the existing Recorder device logic.
2. Level check: read one calibration line; require peak between −12 and −3 dBFS
   with no sample at 0 dBFS.
3. Silence capture, 5 s: measure the noise floor. Pass ≤ −50 dBFS, warn above
   −45 dBFS, block below −35 dBFS with an explanation of what to fix.
4. Capture at the device's native rate (typically 48 kHz) and keep that as the
   master. Derive the 24 kHz training WAV from it. Never capture at 24 kHz.
5. Store the result as a Capture Check on the session, and offer to save the
   silence capture as an Environment Noise Profile — the domain type already
   exists and is already reusable from Control Rack.

### 2. Recording loop — two modes

Cards exist because the engines want 2–15 s samples, not because reading in
fragments is good for the voice. Read card by card and the model learns
sentence-island prosody: each utterance is well formed, but nothing carries
across a sentence boundary. That hurts long-form generation, and it hurts
VibeVoice most, since long-form is what it is built for.

So the Studio offers two modes, and the continuous one is the default.

**Flow mode (default).** The speaker reads the whole passage in one pass, with a
natural pause between cards. The take is split afterwards at silences of 400 ms
or more, and each resulting span is assigned to the card the read-along cursor
was on. No forced alignment is involved: the card order is known and the speaker
moves through it monotonically, so silence plus cursor is enough. If the split
count does not match the card count, the session opens a boundary-review strip
instead of guessing — the user drags the two or three wrong edges and moves on.
Prosody survives, and the samples still come out card-sized.

**Take mode.** One card, one arm, one file. Slower and more clicks, but it is the
right tool for the hard emotional passages, for a noisy room where a long pass
would be wasted, and for retaking a single card out of a finished block.

Either mode: arm → 3-2-1 count-in → 300 ms lead-in silence → speech → auto-stop
after sustained silence (VAD) or manual stop.

On stop — per take in Take mode, per split span in Flow mode — locally and
immediately:

- trim leading/trailing silence, keeping 150 ms of room tone on each side;
- measure peak, RMS, noise floor, clipped-sample count;
- run local STT on the take and score it against the card text with a
  normalized token distance;
- classify `accepted` / `review` / `retake` and auto-advance on `accepted`.

A rejected take is **kept and marked excluded**, never deleted. This repository
does not silently drop provenance.

### 3. Storage

```
<project>/assets/training/reading-sessions/<session-id>/
  session.json          # pack snapshot, card list, takes, QC, coverage
  takes/<card-id>-<n>.wav
  blocks/<emotion>.wav  # rebuilt on block finalize, for review playback
```

All paths project-relative, per `docs/PORTABILITY.md`.

### 4. Media Pool registration

Register **one asset per (session, emotion) block**, not one per card. A 30
minute session is roughly 200 cards; 200 index rows would undo the W1 index work
(`media.list` 3.3 s → 0.094 s, `index.json` 31.3 MB → 3.05 MB). The block asset
carries the concatenated audio and text for review; the per-card detail the
compiler needs lives in `session.json`.

Block assets are created with `captureTier: "guided"`, `trainingSelected: true`,
the session's Speaker Profile, and the passage's Emotion Label already set.

### 5. Reference clip harvesting

At session end, pick the best contiguous 30–60 s of accepted neutral takes by
SNR with no clipping, and save it as the speaker's `reference.wav` +
`reference.txt`. Repeat per emotion for the emotions that have enough accepted
material.

This is the highest-value output in the plan and should land first: it makes
zero-shot cloning work minutes after recording, before any fine-tune exists, and
it is what lets a word tagged `angry` in Script be generated from an angry
reference rather than a neutral one. It connects HQ capture to the emotion
labelling that already ships.

## Read-along word follow

Requirements the owner set: highlight follows the spoken word; misrecognition is
acceptable; on a misread the user is told to carry on rather than repeat, and the
highlight must not stick.

Algorithm:

1. Tokenize the card into words with a normalized form (lowercase, punctuation
   stripped, plus a diacritic-stripped fallback for Vietnamese, since streaming
   ASR frequently drops tone marks).
2. Keep a monotonic `cursor`. On each interim result, take the last few
   recognized tokens and find the best match inside the window
   `[cursor − 2, cursor + 8]` using a short local alignment with a skip penalty.
3. Advance `cursor` past the match. Never rewind more than 2 words, so a repeated
   word cannot drag the teleprompter backwards.
4. If nothing matches for 2.5 s **while VAD reports speech**, advance the cursor
   by one. This is what implements "read past the mistake" — the highlight can
   never stall on a word the speaker skipped.
5. Auto-scroll keeps the current line vertically centred.

Fallbacks, in order: local streaming STT, then VAD-only pacing with a manual
advance key. **Recording never depends on either** — a failed recognizer
degrades the highlight, not the take.

**Privacy: decided — local only.** Chrome's `SpeechRecognition`, used by
`Recorder.tsx` today, sends audio to a Google service, which contradicts Project
Hub's "Dữ liệu project và audio không rời khỏi máy." The owner has settled it:
guided capture uses the local recognizer and nothing else. The browser
recognizer is **not** an opt-in fallback here.

That makes local chunked streaming STT a hard dependency of this plan rather
than a preference. It already sits on the Phase 02 remaining list ("chunked live
transcript while recording") and the Studio sidecar already owns the model, so
the work is a streaming endpoint over an existing seam, not a new engine.

Consequence to accept up front: a local recognizer running during capture
competes with the recording for CPU and GPU. The highlight must therefore run on
a short-window, cheap pass — the accurate pass is what verifies the take after it
stops, not what drives the highlight. If a machine cannot sustain both, the
highlight degrades to VAD pacing. Recording quality is never traded for it.

The browser-recognizer path still live in `Recorder.tsx` on Speech to Text is
outside this plan's scope, but it carries the same contradiction and should be
raised as its own issue.

## Reading packs

Shipped in this plan: `services/api/app/resources/reading-packs/`
(`vi-core-v1.json`, `en-core-v1.json`, plus `README.md` holding the schema).

Each pack carries one `coverage` passage, one articulation `drill`, and one
passage per app Emotion Label except `mix` — 11 passages, 112 cards, ≈11 minutes
of speech per language, every passage far under the 1000-word cap.

**v1 is a starter set and v2 is now on the critical path.** v1 is sized for
zero-shot reference clips across all nine emotions plus a small neutral core. It
is roughly a quarter of the material the owner's minute targets need:

| | v1 has (vi) | v2 target | Factor |
| --- | --- | --- | --- |
| Neutral / normal | ~503 words | ~1,750 words (12.5 min) | ×3.5 |
| Each emotion | ~140 words | ~630 words (4.5 min) | ×4.5 |
| Whole pack | ~1,640 words | ~6,790 words | ×4.1 |

Structure that follows from the targets: neutral needs to become **four to six
passages** rather than one, since 1,750 words in a single passage would break the
owner's own 1,000-word cap and would be brutal to read in one sitting. Each
emotion stays one passage of ~630 words — still one continuous piece in one mood,
which is what the owner asked for, and still under the cap.

v1 stays valid throughout: it is the same schema, and a session simply reports
fewer minutes owed once v2 lands. Sourcing or generating the v2 passages is
research the owner has scheduled separately; it is content work, not engineering,
and it must not block the Studio being built.

Packs are the catalogue. The session snapshots the cards it actually recorded
into `session.json`, so a project that moves keeps its own ground truth even if
the app later ships a different pack version.

## Verification

- A session recorded end to end produces block assets whose transcript is the
  card text, not an STT guess.
- Deliberately misreading one word does not stall the highlight; it advances
  within 2.5 s and the take is classified `review`, not `accepted`.
- Killing the recognizer mid-session leaves the audio intact and only the
  highlight degraded.
- 200 recorded cards add block-count rows to `index.json`, not 200.
- Moving the project folder leaves `session.json` and every take resolvable.
- A speaker with one finished neutral passage has a usable `reference.wav`
  without any training run having been started.
- Train with `HQ only` selected excludes imported footage from the compiled
  manifest, and the warning appears when tiers with a >10 dB noise-floor gap are
  combined.
- Turning the Recorder HQ switch on puts the reading plan in Recorder and the
  teleprompter in Script, and turning it off restores both without losing the
  session.
- A session stopped halfway and reopened later resumes with the correct minutes
  owed per emotion.
- An adapter deliberately trained on a different speaker's audio fails the
  similarity gate and its set does not publish.
- A generation request whose spans resolve to two different Voice Model Sets is
  rejected at job build time.
- No fake checkpoint, no fake training progress, and no claim that an
  unconnected processor ran.

## Dependencies and sequencing

This plan only **adds sources**, so it can run in parallel with 03-02 and 03-03.
Three small things should be absorbed into 03-02 now rather than forcing a
manifest version bump later:

1. The Dataset Manifest carries `captureTier` and a `textProvenance` of
   `script` \| `stt` \| `user` per segment.
2. The compiler reserves a **dev split** (OmniVoice requires one; 5–10% of cards,
   chosen deterministically so re-compiling is stable).
3. Each segment carries an `instruct` string derived from its Emotion Label, so
   the emotion-conditioning probe described above stays available. Exporters
   that cannot use the field drop it.

## Not in this plan

- Running the fine-tune. That stays 03-03.
- A VibeVoice checkout or adapter. This plan only fixes the manifest so an
  exporter can be written without reshaping it.
- Emotion-aware fine-tuning as a distinct training objective. v1 uses emotion for
  labelling, dataset balance, and reference-clip selection; the `instruct`
  conditioning probe belongs to a later plan with its own thresholds.
- Pack v2 content expansion.
- Languages beyond Vietnamese and English.
