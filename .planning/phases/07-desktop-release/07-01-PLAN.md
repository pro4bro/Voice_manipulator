# Phase 07 Plan 01: Model Delivery And The Security Seams

## Goal

Prepare two things the desktop build cannot ship without, and settle their shape
now while the decisions are fresh: how model weights reach an offline install,
and where authentication will attach when there is a second user.

Nothing here changes behaviour. The ports and vocabulary land; the adapters
follow in a later plan.

## Why these two are one plan

They meet at the same place. Model weights are the largest thing the product
moves and the most sensitive thing it produces: a trained voice model is a
working impersonation of a real person. The channel that downloads a base model
is also the channel that would sync a voice model, and that is exactly where
identity has to exist. Designing them apart would settle the transport twice.

## Part 1 — Model delivery

### What is actually on disk today

| Path | Size | What |
| --- | --- | --- |
| `.runtime/omnivoice-studio/models/` | **5.3 GB** | Faster-Whisper checkpoints, pyannote diarization cache |
| `.runtime/omnivoice-studio/installer-cache/` | — | Wheels, including a 2.5 GB torch build |

`MODEL_ROOT` (`services/stt_studio/studio_app/server.py:35`) already centralises
the STT side, and `faster-whisper` fetches on first use through `download_root`.
So the product already downloads models on demand — it just does it implicitly,
with no catalogue, no progress, no verification and no way to see or reclaim the
space.

An installer that bundled this would be several gigabytes before OmniVoice's own
weights are counted. It must not.

### The split that makes offline work

| | Base models | Adapters |
| --- | --- | --- |
| Examples | OmniVoice base, Faster-Whisper, pyannote | Per-emotion LoRA for one speaker |
| Size | 0.5–5 GB | tens of MB |
| Who owns it | everyone, identical bytes | one speaker, one project |
| Where it lives | machine-local shared cache | the project folder / Voice Vault |
| How it arrives | downloaded from a catalogue, verified by hash | produced here, or carried with the project |
| Backed up with the project | no | yes |

This is what makes "install offline, models on demand" coherent: the installer
carries the application, the first run fetches the base models the user's
selected engines need, and everything the user *creates* stays theirs and
portable. It also keeps ADR 0004 intact — a project stays self-contained,
because a base model is a machine resource, not project content.

### Ports to define now

```
ModelDescriptor   id, kind, engine, version, bytes, sha256, source, licence
ModelStore        resolve(id) -> Path | None
                  ensure(id, on_progress) -> Path
                  list_installed() -> [InstalledModel]
                  remove(id) -> None
                  usage() -> disk bytes by model
ModelCatalog      available(engine) -> [ModelDescriptor]
```

Three rules the adapters must obey:

- **Verify by hash before use, not after download.** A truncated 4 GB file that
  loads and produces noise is worse than one that refuses to load.
- **Resume, never restart.** These are gigabytes over a home connection.
- **Never delete a model a project references** without saying which project.

### Runtime residency is a separate problem

Disk is not the scarce resource; VRAM is. The per-emotion decision in plan 03-04
means one speaker can own nine adapters, and they cannot all be resident. The
generation job therefore batches by emotion — every `angry` span in one pass —
so an adapter is loaded once per line rather than once per span. A `ModelStore`
answers "is it on disk"; a later `ModelResidency` answers "is it in VRAM, and
what should be evicted". Do not conflate them.

## Part 1b — What ships inside the app

The question this answers: can a user install nothing and have it work the same
on every machine?

### What the user has to do today

`scripts/setup-pro4bro.ps1` calls `Resolve-Python311`, which searches three
fixed locations and otherwise throws *"Không tìm thấy Python 3.11. Cài Python
3.11..."*. So today the answer is no — the product asks a creator to go and
install a programming language before it will start. That is the barrier worth
removing, and it is removable.

### What can and cannot be bundled

| Layer | Size | In the installer? |
| --- | --- | --- |
| Python 3.11 itself | ~15–40 MB | **Yes.** A standalone build ships in the app folder — no system install, no PATH, no registry. |
| App and pure-Python dependencies | tens of MB | **Yes.** |
| Small binary wheels | tens of MB | **Yes.** |
| torch + CUDA | **3.4 GB** as a wheel, part of the **7.7 GB** installed runtime | **No.** |
| Model weights | **5.3 GB** today | **No.** |
| NVIDIA driver | — | **Impossible.** It is a kernel-mode driver; only the user can install it. |

A bundle carrying all of it is a 13 GB installer, and every user pays it
including the ones who only ever transcribe on a CPU.

### The distinction that actually matters

"Bundled" and "the user installs it" are not the same axis. What the user is
owed is that **they never open a terminal and never type a command** — not that
every byte arrives in the installer.

So: ship the runtime, fetch the weight. The installer carries Python, the app
and everything small; the first run fetches torch and the models through the
same `ModelStore` and progress UI as any other download, with resume and hash
verification. The user sees a progress bar in the app they already opened, which
is a different experience from being told to go and install Python 3.11.

### CPU first, CUDA when it is worth it

Better still, and worth measuring before committing: bundle the **CPU-only**
torch build, which is far smaller than the CUDA one, and fetch the CUDA build
only when a suitable GPU is actually found. Then the base install works on every
machine — slowly where there is no GPU — and gets fast where it can. Verify the
CPU wheel size before this becomes a promise.

### Bundling does not fix "works here, not there"

Most of that problem was never Python. It is:

- **no GPU** — falls back to CPU, and a training run becomes impractical rather
  than merely slow;
- **a driver too old for the CUDA build** — cannot be bundled around;
- **less VRAM** — this machine has 24 GB, and a run tuned for it will fail on an
  8 GB card;
- **disk** — 13 GB of runtime and models has to land somewhere.

None of those are solved by shipping more bytes. They are solved by **a preflight
check that measures and says so**: what was found, what this run needs, and what
to change. "Your card has 8 GB, this run needs about 12, lower `batch_tokens` or
train on CPU at roughly 40× the time" is worth more than any amount of bundling,
and it is the difference between a product that fails clearly and one that fails
mysteriously on somebody else's machine.

## Part 2 — Security seams

### Where the product actually stands

Stated plainly, because the gap between this and how it feels is the risk:

- **There is no authentication anywhere.** Every route answers every caller.
- **The API is reachable from the tailnet** whenever Tailscale Serve is on.
- **`POST /api/reading-packs/passages` writes files** and is unauthenticated by
  the owner's explicit decision (`docs/READING-LIBRARY.md`). It is the first
  route that lets a caller write rather than read.
- **Secrets go to disk in the clear.** `FileAppPreferences` writes the AI review
  API key and the Hugging Face token into `data/preferences.json` as plain JSON.
  Nothing is stored right now, so this is a live hazard rather than a live leak.

None of this is wrong today: one person, one machine, loopback. All of it
becomes wrong the moment there is a second user or the app leaves the machine.

### Ports to define now

```
Principal        id, display_name, roles
Role             owner | admin | moderator | staff | viewer
Capability       read_project | write_project | author_library |
                 run_training | export_voice_model | manage_users
Authentication   identify(request) -> Principal
Authorization    allows(principal, capability) -> bool
SecretStore      put(name, value) / get(name) -> str | None / forget(name)
```

The first adapter is deliberately trivial: a single-owner authentication that
returns one principal holding every capability, because there *is* one user. That
is honest — it checks nothing and claims nothing. It exists so that enabling real
identity later is a swapped adapter and a config flag, not a pass over every
route.

### What encryption can and cannot do here

Encrypting data at rest on a machine that must decrypt it unattended buys very
little: the key has to live on the same disk as the data. It is worth doing only
where the key can be held somewhere the file system is not.

| Data | Verdict |
| --- | --- |
| API keys, HF tokens | **Encrypt via Windows DPAPI**, tied to the user account. Real, cheap, and the current plaintext write should not survive to a shipped build. |
| Voice models | Not at rest on the owner's own machine. **In transit, always**, and that is a transport decision, not a storage one. |
| Project audio | No. It is the user's own material on the user's own disk; encrypting it protects nobody and complicates every tool that reads it. |
| Anything synced to a server | **Yes, and identity first.** This is the case that has to be designed rather than bolted on. |

Do not ship a passphrase prompt that unlocks a key stored beside the data. It
raises the appearance of protection without the substance, which is the same
mistake the authoring password would be if anyone called it access control.

### Sequencing

Real authentication is due **before the second user, or before the app leaves
this machine — whichever comes first.** It is far cheaper to attach to twenty
routes than to eighty, and this API is still small.

## Tasks

1. Add `ModelDescriptor`, `InstalledModel` and the `ModelStore` / `ModelCatalog`
   ports with no adapter, documented as unimplemented.
2. Add `Principal`, `Role`, `Capability` and the `Authentication` /
   `Authorization` / `SecretStore` ports, likewise.
3. Record the base/adapter split in `CONTEXT.md` so later work inherits the
   vocabulary rather than reinventing it.
4. Leave every route untouched. A seam that is defined and unused is honest; a
   seam that always answers yes and is wired in looks like a check.

## Not in this plan

- Any adapter, any route change, any behaviour change.
- Multi-user accounts, SSO, or user management.
- The catalogue server itself.
- Moving the STT models out of `MODEL_ROOT`, which is a migration and needs its
  own plan.
