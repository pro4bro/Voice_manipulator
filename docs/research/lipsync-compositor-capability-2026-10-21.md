# LipSync engines versus compositor requirements

Research date: 2026-10-21. Scope: official repositories and model cards for MuseTalk 1.5, LatentSync 1.6, and Wav2Lip, compared with the requested LipSync editing workflow. This is a source and license review, not a benchmark on project footage or a legal opinion.

## Recommendation

None of the three repositories implements the complete requested workflow. They are inference engines that take video/image frames and audio and produce lip-synced output; none provides a multitrack video/audio editor, editable duplicate/trim/extend clips, persistent speaker-to-face assignments, integration with this product's Speaker Profiles and generated speech-turn timing, or selective re-rendering of voice-over edits. Those are product-owned composition, identity tracking, scheduling, and artifact-lineage features.

Keep MuseTalk 1.5 as the first local inference candidate: its README documents normal and realtime inference, video plus audio inputs, a Windows invocation, and a 256×256 face region. Its maintainer reports 30+ FPS on a V100 for realtime inference, but this is not a quality or runtime guarantee for this app's footage. Evaluate LatentSync 1.6 as a second visual-quality candidate; its 512×512 training addresses blurry mouth/teeth output, at substantially higher VRAM cost. Wav2Lip is useful as a legacy baseline only if use is personal/research/academic or a separate commercial grant is obtained; the public repository explicitly says commercial use is prohibited.

For this product, a robust flow would be: edit video/audio tracks in the app; analyze shot boundaries and detect/track faces in each shot; let the user map stable face tracks to Speaker Profiles; map generated speech turns to timeline intervals; render only intersecting face/video intervals through the selected engine; then composite untouched footage and preserve clip/audio provenance. Re-rendering a changed voice-over span requires invalidating and regenerating the corresponding video segment(s), followed by review and an output artifact. The engines do not supply this orchestration.

## Integration and license notes

- **MuseTalk:** official README offers normal/realtime inference, specifies video/image or folder and audio input, and gives Windows invocation guidance. It describes an aligned 256×256 face region and multilingual audio examples. Maintainer claims are not independent quality evidence. Code and trained model have permissive/commercial statements in its README, but explicitly listed third-party components (Whisper, VAE, DWPose, S3FD, etc.) retain their own terms. Review the exact downloaded checkpoints and notices before bundling. [Official README](https://github.com/TMElyralab/MuseTalk), [code license](https://github.com/TMElyralab/MuseTalk/blob/main/LICENSE), [official weights](https://huggingface.co/TMElyralab/MuseTalk).
- **LatentSync:** the 1.6 changelog says the main change is training at 512×512; the repository documents video/audio inputs and lists 18 GB minimum VRAM for 1.6 inference. The official model card lists OpenRAIL++ and a 9.64 GB model repository. The GitHub Apache-2.0 code license does not replace the weight terms. Its issue tracker contains a report that a two-face video was processed as the first detected face; treat this as corroborating evidence of the missing identity-selection contract, not a formal product guarantee. [Official README](https://github.com/bytedance/LatentSync), [1.6 changelog](https://github.com/bytedance/LatentSync/blob/main/docs/changelog_v1.6.md), [code license](https://github.com/bytedance/LatentSync/blob/main/LICENSE), [1.6 model card](https://huggingface.co/ByteDance/LatentSync-1.6), [multi-face issue](https://github.com/bytedance/LatentSync/issues/207).
- **Wav2Lip:** repository inference includes face detection and options such as face padding, smoothing, and output sizing, but no editable multi-track/speaker identity workflow. The README expressly limits the public code/model/demo to personal/research/academic use. A commercial API is a separate hosted service and license, not the open-source local engine. [Official README](https://github.com/Rudrabha/Wav2Lip), [license statement and history](https://github.com/Rudrabha/Wav2Lip/issues/104).

## Product implications

The requested right-column engine selector can list all three, but should represent code availability, model availability, and permitted usage separately. In particular, installing Wav2Lip source does not grant commercial rights to its public weights. An engine selector alone does not make generation available: each choice still needs a product adapter, compatible isolated runtime, verified model receipts, job lifecycle, cancellation/progress, output validation, and license gate.

The timeline and speaker needs form a product layer shared across engines. Video clip arrangement should retain source asset and source IN/OUT per clip; generated voice turns should retain speaker profile, source output, and timing. Face IDs should be shot-scoped tracks that users explicitly map to profiles, because face detections can disappear or reorder across cuts. When a voice-over span changes, invalidate the corresponding derived lip-sync intervals, render replacements, composite, and retain the prior source/output relation. None of the three engines persists these decisions.
